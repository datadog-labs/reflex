Recovery under pressure
Three read replicas serve a versioned snapshot. A fourth slot can replace a failed replica. Each replica processes up to four reads at a time with a bounded queue; timeouts cancel work in this model. Slowdowns, overload and injected errors reduce useful throughput.
A rebuild transfers 100 MB, then verifies the snapshot. Transfer work reduces serving capacity at its endpoints. Health probes run every 500 ms. A restarted replica passes a one-second readiness check; a stale replica needs a rebuild.
Jev proposes one action at most once per wall-clock second. Reflex checks freshness, state version, readiness, serving-pool safety, cooldowns and recovery limits. A committed rebuild may still fail later. An inference error retains the current plan.
Fixed recovery excludes unhealthy replicas, restores ready members, rebuilds redundancy, and adjusts transfer rate and serving mode using fixed thresholds. Policy changes restart the run with the same seed and client configuration. Jev is asynchronous, so its timing depends on real response latency.
For a repeatable comparison, choose the same incident script and starting client settings for each policy, then export both runs. This is an illustrative simulator, not a benchmark of a production database or consensus protocol.
